### Structured output and Pydantic
We discussed why plain natural-language output is inconvenient for programs.

Pydantic lets us define a data model that specifies the expected fields and their types.

Example:

```python
from pydantic import BaseModel

class ExtractedInfo(BaseModel):
    currency: str
    primary_factor: str
    direction: str
    confidence: float
```

`BaseModel` provides validation and data-handling capabilities. The model defines the expected structure, but it does not guarantee that the underlying economic analysis is factually correct.

### Section 3.3.2 — Function Introspection and Tool Definitions

We explored Python's `inspect` module and how a Python function can be converted into a tool definition that an LLM can understand.

Important concepts:

- `func.__name__`: obtains the function's name.
- `func.__doc__`: obtains its documentation string.
- `inspect.signature(func)`: inspects the function's parameters.
- Parameter annotations: provide information about expected types.
- Default values: help determine which parameters are required.
- JSON Schema: describes the expected structure of tool arguments.
- Tool definitions: describe a function to the LLM, including its name, description, and parameters.

The helper functions developed for this purpose are:

```python
function_to_input_schema(func)
function_to_tool_definition(func)
```

The current implementation is a basic version. More complex type annotations, such as unions, may need additional handling in the future.

### Section 3.3.3 — End-to-End Tool Execution

We created a separate test file:

`test_agent_loop.py`

The script combines the web-search function, function introspection, tool definitions, LLM requests, and tool execution into a basic agent loop.

Its main components are:

- `search_web`: performs the web search.
- `function_to_input_schema`: generates the input schema.
- `function_to_tool_definition`: creates the LLM tool definition.
- `tool_execution`: executes the function requested by the LLM.
- `simple_agent_loop`: manages the interaction between the LLM and the tools.

The central execution flow is:

1. Create the conversation messages, including the system prompt and user question.
2. Send the messages and tool definitions to the LLM.
3. Check whether the assistant response contains tool calls.
4. If tools are requested, append the assistant message to the conversation.
5. Parse the tool arguments from JSON.
6. Execute the corresponding Python function.
7. Append the tool result as a message with role `tool` and the matching `tool_call_id`.
8. Send the updated conversation back to the LLM.
9. Continue until the LLM returns a final answer without another tool call.

The essential insight is that **the LLM does not directly execute Python functions**. It requests a tool call, and the Python program executes the function and returns its result to the LLM.

### Section 3.3.4 — The Challenges of Custom Tools

We discussed the main problems with building and maintaining tools independently:

1. **Different APIs:** Each external service has its own conventions, authentication methods, parameters, and response formats.
2. **Error handling:** Tools must account for timeouts, rate limits, service outages, invalid inputs, and failed requests.
3. **Inconsistent implementations:** Different developers may implement similar tools using different schemas, return formats, or execution models.
4. **Maintenance:** APIs and dependencies change over time, requiring updates to the tools.
5. **Standardization:** A shared protocol can make tools easier to describe, expose, discover, and integrate across different AI systems.

We introduced MCP, the Model Context Protocol, as an approach to standardizing how AI applications connect to external tools and resources.

MCP does not automatically eliminate all integration, reliability, or maintenance problems. It provides a common protocol that can reduce the need for custom integrations.
